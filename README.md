# ASTRAHEALTH AI

**Autonomous astronaut health intelligence for long-duration missions — offline-first, local AI.**
NASA Space Apps Challenge 2026 prototype.

> **Prototype — not a medical device.** ASTRAHEALTH AI does not diagnose and must not be used for real flight
> or clinical decisions. All profiles and readings are **synthetic**. Severity rules are **demonstration
> placeholders** that have not been clinically validated.

ASTRAHEALTH helps a crew member see three things:
- what changed against their own baseline
- how sure the system is
- **what to do to improve it** (the care plan)

Ten local specialist agents analyse validated observations. A deterministic Safety & Evidence Gate assigns
severity from a versioned rule set. An optional local LLM only writes explanations, and every sentence it writes
is validated against the findings.

## What makes it different
- **Personal, not population:** every measurement is compared with the crew member's own baseline.
- **Honest uncertainty:** every finding carries a certainty grade with its reasons.
- **Safety before AI:** severity comes from versioned rules. The local AI only explains, and every sentence it writes
  is checked against the findings.
- **Actionable:** the care plan turns each finding into steps and a personal goal, and tracks progress.
- **Offline and private:** everything runs on the laptop, the app proves it has no external connections, and
  sensitive text is encrypted.

## Quick start (Windows)

```powershell
scripts\setup.ps1      # once, with internet: Python venv, npm install + build, optional `ollama pull qwen2.5:3b`
scripts\start.ps1      # then fully offline: http://127.0.0.1:8765
scripts\run_tests.ps1      # 83 backend + 4 frontend unit + 28 browser tests (flows + WCAG audit, Edge and Chrome)
scripts\verify_offline.ps1 -AdminPin <pin>  # proves no external connections during a full analysis workflow
```

**Demo vs real profiles:** the three crew members marked *(demo)* are **synthetic**: their history is
generated by the app so the agents have data to analyse. Use **+ Add crew member** in the profile menu to create a
real profile; it starts empty, has no mission assigned (the fictional ARES-01 mission is for demo profiles only) and
builds a personal baseline after 7 days of check-ins.

**Secrets:** on first start the app writes `backend/data/INITIAL_SECRETS.txt`. **Note the values down, then delete
the file**, or use the button on the Settings page (admin PIN). `credentials.json` keeps only salted hashes, plus keys wrapped with Windows DPAPI.
- **Medical officer PIN:** clears URGENT alerts, confirms physically implausible values, withdraws symptom
  reports and changes values older than 24 h.
- **Admin PIN:** demo scenarios, fault injection, imports, reset/reseed, knowledge rebuild, backups and the audit log.
  The browser asks for it once per session and keeps it only in memory.
- **Device token:** required to push device records. Devices can never report symptoms.

Five wrong PINs trigger a fixed 60-second cool-down. That limits guessing to about 5 tries a minute without letting another
program lock the medical officer out for long. Failed attempts are audited.

## Crew-facing screens
Overview · Check-in (form, conversation, CSV/JSON import) · **Care Plan** · Health Trends (with correct /
retract / confirm) · Digital Twin (2D, optional 3D) · Routine · Reports (PDF, CSV, print,
passphrase-encrypted PDF).

Notifications live in the **bell** in the top bar. An open URGENT alert also shows a persistent red pill
that only the medical officer can clear. Technical views (agent trace, system status) are linked in the
footer, for reviewers.

## How the system handles its own limits
- **Certainty on every finding:** strong, moderate, limited or self-reported, with the reasons (history length,
  persistence, corroboration by an independent agent, measurement context, data quality).
- **Grounded explanations:**
  - LLM limitation statements must restate a real limitation of the analysis.
  - LLM recommendations must restate an approved next step or care-plan step.
  - Statements implying a diagnosis, medication, alarm or a cause are removed.
- **Personal baselines exclude the last 3 days,** so a developing change doesn't dilute its own reference.
  AnomalyDetect trains on the same window, so agents don't "disagree" just because they use different windows.
- **Unknown is never green.** Real disagreements between agents are escalated, never averaged.

## Deviations from the original stack

| Spec | Implemented | Reason |
|---|---|---|
| scikit-learn IsolationForest | NumPy Isolation Forest | The laptop's Application Control policy blocks scikit-learn's compiled modules. |
| SQLAlchemy / pandas | stdlib `sqlite3` / NumPy | Same policy. |
| Sentence-Transformers + FAISS | BM25 + domain synonym map (NumPy) | No model download; still lexical, not semantic. |
| Port 8000 | 8765 | Port 8000 is used by another program on this laptop. |

## Safety and security behaviour
- An URGENT alert that the medical officer has not acknowledged keeps the overall state URGENT, whatever later
  check-ins, corrections or retractions say.
- One urgent event produces one notification. Review and monitor items are each consolidated into a single
  notification.
- A double-clicked or resent check-in is stored once (idempotent replay).
- Free text (check-in notes, conversation text) is encrypted at rest. Every secret key is
  protected by Windows DPAPI.
- The audit log is **hash-chained**: any edited, deleted or inserted record is detected (`/system/audit`, admin).
- An **encrypted** daily backup is kept (last 5). It is skipped automatically when disk space is low.
- The synthetic demo timeline is kept current hourly while the server runs.
- The local model is warmed up and kept loaded only when at least 6 GB of RAM is free (`LLM_MIN_FREE_RAM_GB`).
  On a smaller laptop it is unloaded a minute after each explanation, so analysis stays under 2 s.
- Times are shown in the viewer's local time zone. Analysis days follow the crew profile's zone.

## Remaining limitations (honest list)
- **Clinical content:** rules, symptom lists, statistical parameters and care-plan steps are demo content
  pending flight-surgeon review. This cannot be fixed in code.
- **Knowledge library:** nine team-written summaries plus one document of short verbatim NASA quotations
  (KB-010, with URLs). Longer official extracts can be added via `knowledge/source_registry.json`.
- **LLM speed:** about 35–120 s per explanation on this CPU-only 7.4 GB laptop, against a 20 s target. It runs in
  the background, one at a time.
- **Security:**
  - Measurement values in the live database are not encrypted (free text and backups are); use BitLocker for full-disk protection.
  - PINs are shared role PINs, not personal accounts.
  - The offline guard covers the Python process, and the browser is restricted by a Content-Security-Policy.
    Ollama is outside the app's control and must be bound to 127.0.0.1.
- **Certainty grades** are rule-based, not calibrated probabilities. InputSense is English-only and rule-based.
- **Accessibility:** the automated WCAG 2.2 A/AA audit (axe-core) passes on every crew screen. A manual
  screen-reader pass is still recommended.
- **Offline rehearsal:** a physical Wi-Fi-off rehearsal on the presentation laptop is still needed.

## Hosted demo (Render)
`render.yaml` + `Dockerfile` deploy a **public demo** on Render's free plan:
- **Synthetic crew only;** it shows a "HOSTED DEMO" label. Do not enter real health data.
- **No local AI model:** the free plan has 512 MB RAM, so explanations use the deterministic template.
  The local model runs on the mission laptop.
- **Demo data is seeded when the image is built,** so a cold start takes seconds. Data resets on every restart.
- **PINs come from Render's secret settings** (`ADMIN_PIN`, `MEDICAL_OFFICER_PIN`). No plain-text secrets are in the image.

Deploy: Render dashboard → **New → Blueprint** → select this repository → enter the two PINs → **Apply**.
